# Восстановление NetBird: этап 1, тестовая версия 1.3.0-r1

Умный guard заменяет прежний цикл, который проверял только наличие процесса.
Он включается только для NetBird, которым управляет приложение (`main.enabled=1`),
и при включённом автозапуске службы NetBird. Существующий внешний NetBird не подключается
и не перерегистрируется автоматически.

## Поведение

- Проверка примерно каждые 30 секунд плюс время выполнения команд; статус ограничен таймаутом.
- Исправное подключение проверяется локально: управление, адрес NetBird и signal (если версия его сообщает).
  В штатном режиме нет дополнительных HTTP-запросов и постоянно работающего ucode-процесса.
- После первого запуска наблюдения — 90 секунд ожидания. Отсутствие процесса подтверждается
  минимум тремя проверками на протяжении 60 секунд. Зависание статуса или длительное отсутствие
  подключения — минимум тремя проверками на протяжении 180 секунд.
- Перед восстановлением проверяется прямой IPv4 HTTPS-доступ через устройство основного
  маршрута к сохранённому management-серверу. Его доступности достаточно для подтверждения
  интернета. При неудаче проверяются 1.1.1.1, затем 1.0.0.1. Proxy-переменные игнорируются,
  TLS проверяется. При недоступности всех точек guard ждёт.
- Для отвечающего, но отключённого клиента дополнительно проверяется сохранённый HTTPS-адрес
  management. Сетевая/TLS-ошибка и HTTP 5xx означают ожидание сервера, без перезапуска агента.
  Это проверка HTTP-доступности, а не полная проверка management gRPC или доступа администратора.
- `Idle` считается ручной остановкой. `NeedsLogin`, `LoginFailed`, `SessionExpired` требуют
  действий администратора; guard не запускает `up`, SSO, logout и не использует setup key.
- Восстановление: только `start` для отсутствующего процесса или `restart` службы.
  После команды — 90 секунд ожидания. Не более трёх попыток за скользящий час,
  с минимальными интервалами 60/300 секунд. Неудачные команды тоже расходуют бюджет.
  Время монотонное, перевод часов/NTP лимит не сбрасывает. Бюджет хранится в RAM до перезагрузки.
- Блокировки NetBird и приложения исключают одновременное восстановление и connect/disconnect,
  обновление пакета, применение подписки или восстановление Xray.
- Нет перезагрузки роутера, изменения DNS/firewall/профиля или удаления регистрации.

Состояние: приватный `/var/run/xtlspro-netbird/guard.json`, доступно также в
`xray-lab-netbird status` и на странице NetBird. В syslog пишутся изменения причины и
попытки восстановления; полный статус клиента и секреты не журналируются.
После обновления приложения перезапускается только supervisor, не сам агент NetBird.

## Проверка на LAB перед выпуском

1. Установить тестовый APK при наличии локального SSH. Подтвердить NetBird, Xray и DNS.
2. Подождать две минуты: guard должен показать `healthy`, без recovery attempts.
3. Завершить процесс демона NetBird, не отключая приложение/автозапуск. Проверить запуск
   (возможен и собственный respawn службы), возвращение адреса и реальный SSH через NetBird.
4. Отключить WAN на несколько минут: `waiting_uplink`, отсутствие циклических перезапусков.
   Вернуть WAN, подтвердить восстановление. Разрешённые ранее попытки в текущем часовом окне
   должны сохраниться.
5. Проверить явное отключение через приложение: агент не должен подниматься самостоятельно.
6. Проверить конкуренцию с обновлением подписки и действиями NetBird.
7. При подвисшем `status`, ошибке регистрации и недоступном management проверить причины
   в изолированной тестовой среде; рабочий сервер ради этого не выключать.

```sh
clear
xray-lab-netbird status
logread -e xray-netbird-guard | tail -n 30
ucode /usr/share/xray/lab/control.uc health
```

Обратный аварийный SSH — следующий этап после проверки guard. Он пока не реализован,
внешний сервер и Telegram-бот в этом изменении не настраиваются.
