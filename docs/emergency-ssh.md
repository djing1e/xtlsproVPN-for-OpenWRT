# Аварийный обратный SSH — тестовая 1.3.0-r4

Роутер использует встроенный Dropbear dbclient и отдельный ключ Ed25519.
Дополнительный VPS или тяжёлый агент не нужны: требуется существующий SSH-сервер.
Telegram-бот не входит в эту версию.

## Что уже проверено вручную

На HOME подтверждены обратный туннель и полноценный вход через MobaXterm с SSH gateway.
SSH самого HOME слушает 222, поэтому назначение туннеля — `127.0.0.1:222`, а локальный
порт на сервере — 22001. Ранее ошибочное назначение на 22 давало reset при подключении.
Фактические адреса, ключи и данные клиентов в пакет и исходники не включаются.

На LAB guard 1.3.0-r1 проверен завершением процесса и SIGSTOP: start/restart восстановили
NetBird с прежним адресом. При потере WAN guard ждал без новой попытки восстановления.
Ручное отключение сохранилось; повторное подключение без setup key успешно.

## Автоматический режим

Резерв по умолчанию отключён. В панели NetBird появляется раздел аварийного SSH.
Сначала создать/показать ключ роутера, настроить сервер и вручную проверить открытие.
Сохранение параметров включает наблюдение и закрывает текущий управляемый туннель.

- После 300 секунд отказа NetBird — попытка открытия туннеля независимо от watchdog Xray.
  Наблюдение использует локальный status NetBird, не повторяет его подключение и не меняет регистрацию.
- Если служба NetBird отключена или daemonStatus Idle, автоматическое открытие подавлено.
  Явная кнопка открытия резерва работает и при отключённом NetBird.
- После устойчиво исправного локального статуса NetBird туннель остаётся ещё 600 секунд.
  Это не подтверждение реального административного входа; перед закрытием администратор должен
  проверить основной доступ. Можно повторно открыть резерв вручную.
- «Открыть» держит резерв 30 минут независимо от состояния NetBird. «Закрыть» подавляет
  автоматическое открытие на 30 минут. «Выключить» отключает резерв постоянно.
- Неудачные запуски повторяются с паузами 30/60/120/300 секунд. Собственного respawn у туннеля нет.
  TCP-соединение без установления за 90 секунд останавливается; дальше применяется тот же backoff.
  Лимиты времени — монотонные, состояние в RAM. После перезагрузки ручные интервалы не сохраняются.
- Запущенный процесс и TCP ESTABLISHED не доказывают успешный проброс или SSH-вход; UI этого не утверждает.

## Маршрутизация и ресурсы

Поддерживается IPv4-адрес сервера без DNS. Перед каждым запуском проверяется совпадение маршрута
с основным uplink; dbclient привязывается к выбранному исходному IPv4. В текущей версии включённый
перехват OUTPUT не поддерживается: запуск отказывается от работы с явной ошибкой.
Отдельные исключения OUTPUT могут быть реализованы позднее. Маршруты и firewall не меняются.

Постоянно работает лёгкий shell supervisor с sleep 30, проверка выполняется коротким ucode-процессом.
dbclient запускается только по аварии или вручную. Фактический RSS dbclient показывается в UI;
его размер на конкретном роутере нужно измерить аппаратно. Autossh и OpenSSH client не устанавливаются.

## Ключи и сервер

Приватный ключ: `/etc/xtlspro-rescue/id_ed25519`, каталог 0700, файл 0600. Через RPC возвращается
только публичная часть. Существующий ключ не заменяется. Каталог внесён в sysupgrade keep.d;
обновление приложения ключ не перезаписывает. При удалении приложения ключ намеренно остаётся.

Публичный ключ сервера получается через уже доверенный доступ администратора и сохраняется в UCI.
Перед запуском закрепляется в root known_hosts; несовпадающая существующая запись не заменяется автоматически.
Dropbear запускается с StrictHostKeyChecking=yes, BatchMode=yes, PasswordAuthentication=no,
ExitOnForwardFailure=yes. Отключения проверки host key нет.

Сервер настраивается отдельно. Для пользователя туннелей: AuthenticationMethods publickey,
AllowTcpForwarding remote, GatewayPorts no, MaxSessions 0, PermitOpen none; запрещены TTY,
agent/X11/stream-local forwarding. PermitListen ограничивается выделенными loopback-портами.
В authorized_keys каждого роутера: restrict,port-forwarding,permitlisten="127.0.0.1:PORT".
Для каждого устройства нужен отдельный ключ и отдельный порт. При добавлении портов нужно
обновить и серверный PermitListen. Публичные listener-порты в firewall не открываются.

Ключ туннеля не даёт входа на роутер: администратор отдельно авторизуется своим ключом HOME,
через SSH gateway сервера. Приватные административные ключи остаются на ПК.

## Проверка после установки

Необходимо остановить старую ручную команду dbclient через Ctrl+C, чтобы освободить серверный порт.
Не завершать все dbclient/ssh процессы и не закрывать единственную рабочую административную сессию.
На HOME использовать подтверждённые ключ и адрес из ручной настройки, порт роутера 222.

1. Создать/показать ключ, проверить совпадение с уже разрешённым на сервере.
2. Сохранить параметры; открыть на 30 минут. Проверить listener на сервере и полноценный SSH-вход.
3. Проверить GUI/CLI «Закрыть», затем ручное открытие при выключенном NetBird.
4. Имитировать отказ NetBird без ручного отключения автозапуска; после 5 минут проверить резерв.
   Исправный guard может восстановить NetBird раньше — тогда резерв открываться не должен.
5. Проверить отсутствие WAN и восстановление, разрыв SSH к серверу и повторный запуск.
6. Вернуть NetBird и проверить десятиминутную задержку закрытия. Сохранить локальный SSH на время теста.

```sh
clear
xray-lab-rescue status
logread -e xray-rescue | tail -n 30
```

На HOME проверены полноценный вход через новую службу, закрытие и повторное открытие из UI,
автоматический перезапуск после SIGTERM клиента, открытие после 306 секунд отказа NetBird
при SIGSTOP и автоматическое закрытие через 627 секунд после обнаружения восстановления.
Клиент занимал примерно 0,86–0,95 МиБ RSS. TCP ESTABLISHED при автоматическом открытии
подтверждён; полноценный административный вход подтверждён в ручном режиме.

Исправления после испытаний: runner удаляет унаследованный HOME, чтобы Dropbear получил
домашний каталог root через getpwuid() и прочитал закреплённый known_hosts. Автозапуск
NetBird распознаётся как через обычную службу, так и через netbird-wrapper; неподдерживаемая
команда enabled старого клиентского скрипта не подавляет резерв при включённом wrapper.
На HOME wrapper управляет существующим NetBird, guard приложения пока его не обслуживает.

Остаются аппаратные проверки: установка итогового r4, сохранение настроек/ключа и автозапуск
после перезагрузки, потеря и возврат WAN, недоступность сервера аварийного SSH.

В r4 прямой start init-скрипта туннеля (включая автоматический вызов APK post-install/upgrade) не запускает клиент. Контроллер вызывает start policy только после решения политики и проверки плана. Это исключает запуск устаревшей команды из RAM во время обновления.
