# NetBird: первый этап административного доступа (ветка v1.1.0)

Постоянный доступ к самому роутеру через self-hosted NetBird, обычные SSH и LuCI.
Запросы разрешения пользователю и временные сеансы в этом этапе не реализуются.
Это тестовая интеграция для OpenWrt 25.12.5 / aarch64, не изменение стабильного v1.0.0.

## Что добавлено

- Настройки → Административный доступ: установка, подключение, отключение и статус.
- NetBird ставится отдельно командой `apk add netbird` из настроенного официального
  репозитория OpenWrt; бинарник и регистрационные ключи в APK xtlsproVPN не входят.
- URL management server, необязательное имя устройства и setup key для регистрации.
  Адрес требует HTTPS с действительным сертификатом. В этом этапе поле принимает
  DNS-имя или IPv4; IPv6-литерал и URL с учётными данными не поддерживаются.
- Setup key передаётся через stdin, кратковременно хранится в приватном файле
  RAM (0600), передаётся NetBird через `--setup-key-file` и удаляется после операции.
  В UCI, JSON статуса и аргументах процессов самого значения ключа нет.
- При подключении задаются `--disable-dns=true`, `--disable-client-routes=true`,
  `--disable-server-routes=true`, `--allow-server-ssh=false`. Используется `wt0`.
  Встроенный SSH NetBird не используется, авторизация обычных SSH/LuCI сохраняется.
- У подключённого клиента сначала выполняется `down`: иначе некоторые версии
  NetBird отвечают Already connected и не применяют параметры нового `up`.
- Для новой зоны `xtls_nb` разрешены только входящие TCP 22/80/443 к роутеру;
  forwarding запрещён, LAN routes, masquerade и публикация домашней сети не добавляются.
  Если wt0 уже относится к чужой зоне (напрямую или через network), эта зона сохраняется.
  В таком случае доступ по нужным портам проверяет администратор. Нестандартные
  порты SSH/uHTTPd в первом этапе настраиваются вручную в firewall.
- Подключение включает штатный автозапуск NetBird. Отдельный лёгкий procd guard
  проверяет наличие процесса каждые 30 секунд и запускает пропавший daemon;
  недоступность интернета не вызывает перезапусков. Жизненный цикл Xray не меняется.
- Отключение останавливает NetBird и guard и выключает их автозапуск. Идентичность
  зарегистрированного устройства остаётся для повторного подключения.
- Статус показывает адрес, management/signal connection, версию, размер бинарника,
  RSS процесса, автозапуск и результат последней фоновой операции.

Сама установка APK xtlsproVPN не устанавливает NetBird, не регистрирует роутер
и не включает этот guard. Существующая установка NetBird при нажатии
«Установить NetBird» остаётся без изменений. «Подключить / применить» управляет
тем же системным клиентом и может прервать существующее NetBird-соединение.

## Сервер

На self-hosted сервере подготовьте группу роутеров и политику от устройств
администратора к этой группе на требуемых портах. Проверьте остальные политики,
в том числе Default/All-to-All: разрешающая общая политика не отменяется более
узкой политикой. Setup key создаётся администратором сервера; API token сервера
на роутере не нужен. Для каждого роутера должна сохраняться собственная
идентичность — её нельзя копировать вместе с резервной копией на другой роутер.

В UI укажите URL сервера и setup key, затем нажмите «Подключить / применить».
После регистрации откройте LuCI или SSH по NetBird IP. Проверка management
connection в UI сама по себе ещё не доказывает доступ от компьютера администратора.

## Проверки перед выпуском

Изолированные тесты исполняют настоящий ucode-контроллер с имитацией NetBird,
APK, служб и UCI: регистрация, защищённые параметры, существующая зона, отказ
сервера, откат наших разделов при ошибке firewall, отключение и очистка ключа.
Shell launcher проверяется с настоящим flock и конкурирующими действиями.

Обязательная следующая проверка на LAB:

1. Установка клиента, регистрация на реальном сервере, SSH/LuCI с компьютера администратора.
2. Проверка свободного flash, бинарника и RSS до/после подключения.
3. Остановка/запуск Xray, обновление подписки и перезапуск firewall при активном SSH.
4. Аварийное питание, восстановление uplink без ручного перезапуска.
5. Пропажа процесса NetBird — guard восстанавливает его; ручное отключение сохраняется после reboot.
6. Отказ регистрации, неверный ключ и временная недоступность management/relay.
7. Существующий NetBird: ключ не теряется, чужие зоны firewall не переписываются.

Ограничение первого этапа: хотя NetBird не меняет системный DNS и не направляет
пользовательский интернет через себя, разрешение DNS-имён management/signal/relay
остаётся зависимым от работающего резолвера роутера. Изолированного bootstrap DNS
для административного канала пока нет. Нельзя объявлять его полностью независимым
от поломки DNS. При пропаже upstream-интернета удалённый доступ также недоступен.
Фактическое взаимодействие nftables NetBird и firewall4 требует проверки на устройстве.
